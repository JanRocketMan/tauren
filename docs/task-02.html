Concepts

Two kinds of tool objects

Task 01 gave you ToolCall: what the assistant records when it asks for a tool. This sounds similar to an AgentTool, but the two are not the same role: 

ToolCall      what the assistant asks for  (id, name, arguments)
AgentTool     what the agent knows how to run  (name, description, schema, executor)
AgentToolResult  what running a tool produced  (tool_call_id, name, content, ok)

The future agent loop will match each ToolCall to an AgentTool by name, run its executor, and convert the result into a ToolResultMessage on the transcript. That is why AgentToolResult mirrors ToolResultMessage without the timestamp: the loop stamps time when it converts, because time is a transcript concern, not a tool concern.

The executor contract

Every tool runs through the same async signature:

executor(tool_call_id, arguments) -> AgentToolResult

The call id lets the result be matched back to the assistant's request. The arguments are the JSON-like values from the ToolCall. Tools do I/O, so the executor is async and the agent loop will await it. An AgentTool is a dataclass that carries this callable; its execute method is a thin async wrapper that delegates.

Why events exist

Events are how the portable agent layer reports progress without knowing who is listening:

Agent loop emits events
        |
        |--> print-mode CLI consumes
        |--> Rich renderers consume
        |--> Textual TUI consumes
        |--> tests inspect

Later tasks build the loop and the frontends. This task builds the vocabulary the loop will emit and the frontends will consume: one event per moment of a session.

The discriminator pattern

Every event carries a type field whose value is a string literal that names the event. The AgentEvent union is the closed set of all events, exactly like AgentMessage is the closed set of messages. A consumer reads event.type via isinstance branches, the same way message_text in task 01 dispatches on message types.

The pattern is deliberately repetitive:

@dataclass(frozen=True, slots=True)
class AgentStartEvent:
    """The agent run started."""

    type: Literal["agent_start"] = "agent_start"

Ten small classes, one per moment, each with the same shape. Do not fight the repetition. It is the point: every event announces itself past a stable string so frontends can map type to renderer.

The event spec

Build one dataclass per row. Defaults: messages, tool_results and args default to an empty collection; type always defaults to its own literal.

Eventtype valueFields besides type
AgentStartEventagent_startnone
AgentEndEventagent_endmessages: list[AgentMessage]
TurnStartEventturn_startnone
TurnEndEventturn_endmessage: AgentMessage, tool_results: list[ToolResultMessage]
MessageStartEventmessage_startmessage: AgentMessage
MessageDeltaEventmessage_deltatext: str
MessageEndEventmessage_endmessage: AgentMessage
ToolExecutionStartEventtool_execution_starttool_call_id: str, tool_name: str, args: dict[str, JSONValue]
ToolExecutionUpdateEventtool_execution_updatetool_call_id: str, tool_name: str, partial_result: AgentToolResult
ToolExecutionEndEventtool_execution_endtool_call_id: str, tool_name: str, result: AgentToolResult, is_error: bool

Then close the set:

type AgentEvent = (
    AgentStartEvent
    | AgentEndEvent
    | ...
)

A future session run will produce a stream like this, and every frontend will read it from the same union:

agent_start
turn_start
message_start        AssistantMessage begins
message_delta        "I'll inspect the file."
message_end          AssistantMessage(... tool_calls=[read])
tool_execution_start
tool_execution_end   AgentToolResult(...)
turn_end
agent_end
The union cannot be proven by the tests alone: annotations are not checked at runtime. mypy and ty will flag a misspelled class name once the module exists, and the teacher reviews the union by reading it. List every event from the table, not a subset.

An honest warning about is_error

ToolExecutionEndEvent.is_error has no default. The loop must always know whether a tool failed. A field without a default forces the caller to decide. Notice how that mirrors ok on ToolResultMessage: defaults exist where a sensible value exists (success is the common case), and stay absent where forgetting to decide would hide a bug.
